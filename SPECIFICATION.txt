Build a complete, production-grade AI/ML system for cricket that predicts how many runs will be scored in the NEXT OVER of a live match, how many runs a specific batter is expected to score in that over, wicket probability, boundary probability, and a statistically valid confidence/prediction interval.

The system must be designed as a real predictive ML application, not as a rule-based demo and not as a chatbot.

The final system must support:

1. Historical model training.
2. Feature engineering from ball-by-ball data.
3. Model evaluation without data leakage.
4. Batter-specific predictions.
5. Team next-over predictions.
6. Bowler runs-conceded prediction.
7. Wicket probability.
8. Boundary probability.
9. Six probability.
10. Confidence/prediction intervals.
11. Live cricket data ingestion.
12. Real-time inference.
13. Dashboard/API output.
14. Model retraining.
15. Model monitoring.
16. Explainability.
17. Proper testing.
18. Reproducible experiments.

==================================================
CORE PREDICTION GOAL
====================

At the beginning of every over, predict:

A. Expected total runs in the next over.

B. Expected runs scored by the current batter.

C. Expected runs scored by the non-striker.

D. Probability of at least one wicket in the over.

E. Probability of at least one boundary.

F. Probability of at least one six.

G. Probability that the over falls into these ranges:

0–4 runs
5–7 runs
8–10 runs
11–14 runs
15–19 runs
20+ runs

H. Lower and upper prediction interval for total runs.

Example final prediction:

Next Over Prediction

Expected Runs: 10.4
Most Likely Range: 8–12
80% Prediction Interval: 5–15

Current Batter Expected Runs: 7.1
Non-Striker Expected Runs: 2.3
Extras Expected: 1.0

Probability of 10+ Runs: 61%
Probability of Wicket: 18%
Probability of Boundary: 72%
Probability of Six: 34%

Prediction Reliability: High

Do NOT manufacture confidence percentages.

Confidence must be based on statistically valid uncertainty estimation or calibrated probabilities.

IMPORTANT MODEL-QUALITY REQUIREMENT
===================================

Do NOT claim or fabricate 98–99% accuracy.

The project should attempt to achieve the highest genuine performance possible.

For regression, measure:

MAE
RMSE
R²
Median Absolute Error

For classification, measure:

Accuracy
Precision
Recall
F1 Score
ROC-AUC where applicable
Log Loss
Brier Score

For uncertainty estimates, measure:

Prediction Interval Coverage Probability
Average Prediction Interval Width
Calibration Error

If any 98–99% score is achieved, validate that it is genuine and is not caused by:

data leakage
target leakage
duplicate matches
future player statistics
random train/test contamination
using information from the predicted over
using post-match information
overfitting

Never optimize metrics dishonestly.

The actual objective is maximum GENERALIZATION on unseen future matches.

PHASE 7 — DATA LEAKAGE PREVENTION
=================================

This section is CRITICAL.

Do not randomly split individual rows.

Use chronological splitting.

Example:

Training:
2010–2023

Validation:
2024

Testing:
2025 onward

If more recent seasons exist, use the latest completely unseen season as the final test set.

The final test set must remain untouched until model selection is complete.

Any statistics such as:

batter career strike rate
bowler economy
venue average
head-to-head statistics

must be computed using only data available BEFORE that match.

Create automated leakage tests.

==================================================
PHASE 12 — BATTER-SPECIFIC MODEL
================================

Predicting individual batter runs is harder because the batter may not face all six deliveries.

Consider a two-stage approach.

Model A:

Predict expected balls faced during next over.

Model B:

Predict expected runs per ball.

Then calculate:

expected batter runs =
expected balls faced × expected runs per ball

Also train a direct batter-over regression model and compare both approaches.

Use whichever performs better.
